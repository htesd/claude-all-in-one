# 架构重构计划（2026-09-10）

状态：三个 CLI reviewer 已完成，主审已按证据修订。本轮只审查代码并制定计划，不修改业务代码、不部署。

## 目标和范围

对照 `ARCHITECTURE.md` 的原始边界，先修复重复执行与共享状态一致性问题，再减少重复编排。
保留 router/worker 多进程、固定出口、两级亲和、Anthropic IR、provider 独立 crate、SQLite
和 bot 池隔离。原设计的四个 crate 是当时单 provider 的规模选择，不撤销现有多 provider。

本轮范围是 `claude-all-in-one`；其他仓库不动。当前 GrokBot 功能改动尚未提交，实施前应
记录文件清单、基准版本和验证证据，将已完成功能与后续重构分开提交；不覆盖现有工作区。
用户已有的临时说明文件不纳入重构。

## 阶段与依赖

按 R0 → R1 → R2 → R3 → R4 → R5 顺序，逐项验证、逐项审查。每项独立验收和交付；
回滚必须遵守末尾的写入方交接约束，旧镜像能启动不等于旧写入逻辑仍安全。
R1–R3 为首批；R4–R5 在首批稳定后进行。修复行为的提交和只移动模块的提交分开。

- 实施前运行 `cargo test --workspace`，记录当次结果；上一轮是 1,744 项通过，不冒充本轮结果。
- 列出三种入口（Messages、Chat Completions、Responses）与流式/非流式覆盖关系。
- 整理测试替身：本地 HTTP worker、可编排的 fake Provider、可注入写失败的临时 SQLite/Store。

### R1：收紧两层请求重放（P0，拆成两个修复提交）

R1a 位置：`crates/gw-app/src/router/mod.rs::forward_to`、转发与 failover 辅助函数。

- 区分“确定连接未建立”“worker 明确未处理该入口”“送达未知”“已开始返回响应”。
- 未知送达或已收到响应后出错，不自动重发，不因为该次错误删除已有亲和。
- 对确定未连接保留当前同组受限故障转移；这是现有行为的兼容选择，不趁机新增路由策略开关。
  原设计默认不迁移与现实现的差异需要在演进说明中明确，后续是否调整默认值另行决定。
- 当前 worker 的业务错误会映射成 400/529/502，并未证实上游 404 直接透传。404 的工作
  是明确 router/worker 契约：只有 worker 明确未挂入口才可迁移，不能泛化成任何 404。
  优先最小内部标记与新旧组合测试，不建设能力注册系统；旧 worker 无标记时保守返回。
- 将决定是否重放的判断集中在 router 内部；不扩展成跨 provider 的全局重试框架。

验收：

1. A 完整接收 POST 后在响应头前断开，B 收到请求数必须为 0，原亲和保留。
2. A 连接拒绝时仅在允许的同组候选内尝试，次数有界，跨组 B 始终收不到请求。
3. worker 明确缺少协议入口可选择有能力的同组 worker；业务/上游 404 不重放。
4. 已收到响应头后断流不重发；三种入口都满足以上契约，对外错误仍符合各入口格式。

R1b 位置：box 的 `Gateway::command` / `sendPrompt` 准备握手、worker 错误分支与
`gw-core::UpstreamError` 的送达语义。当前 `sendPrompt` 可能已执行但确认丢失，此时
`ServerError` 经 readiness 返回，worker 仍可能换号重发。只修 router 不能封住这条路径。

- 将“是否向客户端输出”与“是否可能已提交上游”分开；未知送达是 provider 报告的事实，
  重试决定由 worker 作出。健康分类与重放资格分开，不能伪装成 `BadRequest` 来停止重试。
- 对 box 消息提交后的确认丢失，停止自动同号/换号重发。能按 nonce 查证时只恢复读取；
  查证失败仍按未知处理。interrupt/delete 的尽力清理不能证明原操作没有执行。
- 创建、附件上传、订阅事件流等明确未提交消息的失败，继续适用既有有限恢复策略。
- 用最小契约补齐调用链，不把所有协议一次重写；逐个盘点其他 provider 的送达未知错误
  来源，列出尚未标注的覆盖缺口，不能把新增字段默认值当作全链路保证。

验收：fake gateway 接受 `sendPrompt` 后断开响应，整个 worker 请求只提交一次；准备阶段
明确未发送消息的失败仍能按预算恢复；取消/清理失败不会让下一账号再次提交同一轮。

### R2：凭据与普通 extra 增量分离（P1）

位置：`admin/accounts.rs::update_account`；`worker/mod.rs` 刷新、脏数据回写和 provider 更新接收；`worker/scheduler.rs` 的账号同步；
`gw-core/src/provider.rs` 的更新契约；Cursor 更新生产方；`gw-store` 必要的原子写接口。

分成独立行为修复：R2a 管理端原子更新；R2b 待写增量与同步快照准入；R2c 生产方队列与
停机收尾；R2d 孪生身份守卫。全部通过后再另作模块提取提交，避免一个提交同时改变所有写者。
Store 实际实现位于 `crates/gw-store/src/lib.rs`，原设计的 `control.rs` 尚未成为现有文件。

- 先枚举所有 extra 写入来源：认证刷新、后台驱动回传、配额回填、管理员 patch、账号同步、
  孪生链恢复与停机排空，写清各字段的所有者与覆盖规则。
- 待重试状态保存字段增量及必要版本依据，停止重试写回完整旧 `Account.extra`。
- 凭据更新保留单飞、锁内重读、新旧判定；普通运行时 patch 独立处理，相同/过旧 token
  不得连带丢掉新的 agent id。敏感值不进入日志。
- 明确同一字段的新旧 patch 合并和成功确认规则，防止一次旧写入成功清掉后来追加的待写增量。
- 一次普通字段写入成功，也不能清掉之前失败的 token 增量；反方向同理。
- 即使所有 DB 写入都成功，sync 仍可能在读取 T0 后被刷新线程抢先写入 T1，随后发布旧快照。
  同步发布要有版本准入/保留较新本地更新的规则，不能只看当时的 dirty 位。
- 管理员编辑和多进程写入不受 worker 内存锁保护：核对是否需要 Store 事务内条件更新；
  仅靠进程内 mutex 不能宣称已解决并发覆盖。
- 管理端 `extra_merge` 当前也是先读旧值、合并、再整体替换，必须改为 Store 内原子 patch；
  脱敏哨兵表示“保留写入当时的值”，不能在 handler 中提前还原成旧 token。整体替换仍保留
  显式语义与凭据删除守卫，但校验和写入要基于同一事务状态或明确版本条件。
- 行为测试通过后，提取 `worker/credentials.rs`（暂定名）。只把共享一致性编排移入，
  OAuth 网络协议仍归 provider，SQLite 实现仍归 store。
- Cursor CLI 更新生产方也要按同源的新旧依据合并，不能让迟到旧观测覆盖尚未消费的新观测。
  停机顺序为停止并等待凭据生产方 → 最后采纳 provider 队列 → flush 待写增量 → 退出。
  覆盖现有后台刷新任务，暂不建立通用后台任务框架。DB 条件写也不能替代 OAuth 刷新的
  单一所有者；同一账号不允许两个进程同时刷新，升级交接必须保证这一点。

验收：

1. 首次落库失败 → 管理员更改 proxy/region → 重试：凭据落库且管理员字段保留。
2. 相同/过期 token 和新 agent id 同批返回：拒绝旧凭据但保留合法普通更新。
3. 写入过程中又发生更新：仅确认已写入版本，新的待写状态不丢失。
4. 账号同步、定时 flush、刷新及停机排空交错：最新凭据不回退，失败仍可重试。
5. 使用两个独立 Store 连接复核并发写，不把内存 fake Store 的串行结果视为 SQLite 并发证明。
6. token 写失败 → agent id 写成功 → sync：仍保留并最终写入新 token；账号不存在的
   `Ok(false)` 与真正写入成功分开处理，不记录虚假成功。
7. admin 读到旧账号 → worker 落库新 token → admin patch pool/driver 或提交脱敏哨兵：
   新 token 保留；显式替换/清空凭据仍遵循原 API 的授权与删除守卫。
8. 屏障控制 sync 读取 T0 → 刷新 T1 并写成功、清脏 → 发布 sync 快照：内存仍为 T1。
9. 队列先收到新凭据再收到迟到旧观测：消费新凭据；退出前刚捕获的更新最终进入 DB，
   flush 后不再有生产方追加未保存状态。

R2 的身份阻塞项：导入侧因 `client_id` 不同而创建孪生记录并设置 `twin_of`，恢复侧却把
`twin_of` 当作共享认证链。两者语义冲突已有代码证据，须核对 provider/注册身份/出口归属，
禁止仅凭该字段复制凭据。使用合成 IdC 账号测试不同注册身份不借链；共享链的合法情形需
有明确身份依据，不能顺手复制完整源账号或取消出口隔离。

### R3：统一 worker 请求级重试上下文（P1）

位置：`worker/mod.rs` 请求循环、`finish_response`、非流式收集、`stream_response`。

- 先列出现有 token 修复、profileArn 修复、过载退避、账号切换的预算与触发条件。
- R3a 先定点传递已有“已恢复”状态和成员视图，并修复非流式已产出后重放；之后再决定
  `RetryContext` 的最小字段与恢复函数范围，不要求先搭完整协调器才能修复。
- 建立一个请求级 `RetryContext`：成员视图、已尝试账号/次数、认证恢复状态、当前输出阶段。
  账号级与整请求级计数的范围须明确，不能用一个布尔值合并不同语义。
- 同步报错、非流式抽干、流式首帧报错共用恢复判断与准入函数；HTTP/SSE 输出分别保留。
- 同步刷新后继续携带上下文，不在 `finish_response` 内重置；追加调用都使用同一成员视图
  做 RPM/暖机准入。刷新冷却不等价于推理调用次数限制。
- 不扩大当前重试范围：已经向客户端发出内容、上游送达未知等状态均须保守处理。
  保留 GrokBot 创建/上传/发消息准备阶段的 readiness 错误传播契约。
- 行为稳定后提取 `worker/retry.rs`；避免同时搬动计费、日志、web search 和所有 handler。

验收：

1. 同一 fake Provider 故障序列分别走三条路径，对比推理/刷新次数、RPM、健康状态。
2. 同步刷新成功后流首帧再次认证失败，不因上下文重置额外重试。
3. 分组低优成员与账号默认高优冲突时，各路径均按成员视图准入。
4. 预算耗尽、客户端取消、已经输出内容：无额外推理、无重复终态/计费，租约归还。
5. 准备失败仍能按既有预算换账号；已接纳的云端操作失败不得因此新增隐式重放。
6. 非流式已收集正文/工具事件后发生认证错误，也不能仅凭“尚未发 HTTP 响应”重发。
   错误以 `Err` 与 SSE `error` 两种表示注入，恢复与健康处理须符合相同契约。
   失败尝试已报告的 Usage 不因递归重试丢弃；结算规则必须明确，不能直接算成零用量。

三条路径需要符合各自契约，而非强行调用次数一致：仅发生一次明确的认证拒绝且预算允许时，
预期原调用 + 一次认证恢复调用；同步恢复后又流内失败不应出现第三次推理；RPM 拦住则没有
追加推理；普通流首帧错误保持不换号；已有正文/提交未知后失败一律没有追加推理。profileArn
修复与过载退避继续使用各自原预算，测试分别列举，不能借统一代码扩大它们的适用范围。

R3b 独立修复 Temporal 会话状态：当前 `ensure_agent` 成功会自动选 Temporal，门控缓存还会
到期；它并非需要人工开启的休眠分支。将续接判断放入 run gate 后，并比较 system/tools head。
验收并发同会话排队与 schema/head 改动，不借 box 的测试替代；无需因此重写整个 Temporal。

## 验证、审查与部署

- 每个阶段先用回归用例证实风险，最小修复通过后再提取模块；执行相关测试和
  `git diff --check`。阶段完成运行全 workspace 测试，再经实际 `codex exec` 对抗审查。
- 文档/计划阶段不重复消费生产上游额度；目前没有把新故障序列标为已通过。
- 最终验收使用真实 Claude Code 和 OpenCode，Bash 必须读取测试机新生成的随机内容，
  检查实际本地执行及 tool_result 回传，不能只看模型说“执行成功”。图片/PDF 使用合成材料，
  校验内容不预先泄露到提示中；保留脱敏证据。
- 影响共享 worker 逻辑的 R2/R3/R4 还需覆盖 Kiro、Cursor 和 Dario 的契约与实际可用账号
  冒烟，不用 GrokBot 单一路径代表所有 provider。缺少可用账号时明确缺口，不跳过宣称通过。
- 先构建不可变镜像，记录受影响服务及其原镜像；R1 涉及 router，R2/R3 涉及共享 worker，
  不能沿用上一轮“只更新 bot worker”的部署范围。兼容滚动升级期间的新旧进程共存。
- R2 必须覆盖 router 管理写入方及持有相关账号的全部 worker。旧写入方仍会整块覆盖，
  “旧镜像能读新 DB”不是一致性保证：升级前停止相关管理修改、排空请求及后台凭据写入，
  再切换对应写入方；若旧版不支持后台排空，受控停止旧进程后再启动新版，不能让同一账号
  的新旧写者重叠运行。R1 若新增内部能力标记，也需明确旧 worker 无标记时的保守处理。
- 每阶段 CHANGELOG 记录行为变化、设计理由、迁移/回滚限制；有 DB 变更则优先采用向后
  兼容增量，并验证旧镜像可读。观察重复执行、5xx、刷新失败、待写增量、亲和迁移与工具完成。
- 保留旧镜像和配置快照；回滚代码不回滚已经轮换的新 token，不用旧 DB 全量覆盖线上数据。
